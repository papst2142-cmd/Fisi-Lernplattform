WARUM GIT?
---------------------------------------------------------------------------
Dieser Ordner ist ein Git-Repository (zu erkennen am versteckten
Unterordner ".git"). Git merkt sich bei jeder Sicherung ("Commit") den
kompletten Zustand aller Dateien. Das bedeutet konkret:

  * Nichts geht verloren. Auch wenn eine Datei ueberschrieben wird, bleibt
    der alte Stand in der Git-Historie erhalten und kann jederzeit
    wiederhergestellt werden.
  * Vor jeder Sicherung ist genau zu sehen, was sich geaendert hat (Zeile
    fuer Zeile).
  * Jederzeit laesst sich zu einer frueheren Version zurueckspringen.

Zusaetzlich liegt das Projekt auf GitHub:
  https://github.com/papst2142-cmd/Fisi-Lernplattform
Dort wird jeder Stand zusaetzlich gesichert, und GitHub baut daraus die
Installer fuer Windows, Linux und macOS (siehe INSTALLER-ANLEITUNG.txt).

Das Repository ist oeffentlich: Jeder kann den Code lesen, herunterladen
und Aenderungen vorschlagen. Veraendern kann ihn aber nur der Eigentuemer
(papst2142-cmd) - Vorschlaege anderer ("Pull Requests") werden nur
uebernommen, wenn der Eigentuemer sie ausdruecklich annimmt.

DIE WICHTIGSTEN BEFEHLE
---------------------------------------------------------------------------
Alle Befehle im Terminal eingeben, das im Programmordner (dem Ordner mit
dem Unterordner ".git") geoeffnet wurde. Unter Windows: Ordner im Explorer
oeffnen, in die Adresszeile klicken, "cmd" eintippen, Enter.

  git status
      Zeigt, welche Dateien seit der letzten Sicherung geaendert wurden.

  git diff
      Zeigt Zeile fuer Zeile, was sich geaendert hat (gruen = neu,
      rot = entfernt). Mit [Q] verlassen.

  git add -A
      Merkt alle geaenderten Dateien fuer die naechste Sicherung vor.

  git commit -m "Kurze Beschreibung der Aenderung"
      Sichert den aktuellen Stand dauerhaft in der lokalen Historie.

  git push
      Laedt alle neuen Sicherungen zu GitHub hoch.

  git pull
      Holt Aenderungen von GitHub (z.B. wenn auf einem anderen Rechner
      gearbeitet wurde).

  git log --oneline
      Liste aller bisherigen Sicherungen (neueste zuerst).

  git checkout -- <Dateiname>
      Verwirft noch nicht gesicherte Aenderungen an genau dieser Datei.


SO LAEUFT EIN UPDATE KUENFTIG AB
---------------------------------------------------------------------------
Normalerweise erledigt Claude Code alle Schritte selbst:

  1. Code aendern und testen.
  2. Neue Version setzen - bei einem Update z.B. 0.22, bei einer
     Fehlerbehebung z.B. 0.22.1 (Schema siehe LIESMICH.txt):
       python build.py --setze-version 0.22
     und in AENDERUNGEN.md die Neuerungen unter "## 0.22" eintragen.
  3. Sichern und zu GitHub hochladen:
       git add -A
       git commit -m "Beschreibung der Aenderung"
       git push
  4. Release ausloesen mit einem Versions-Tag:
       git tag -a v0.22 -m "Beschreibung"
       git push origin v0.22
     GitHub baut dann alle Installer, testet sie und veroeffentlicht sie
     unter "Releases".

Selbst nachvollziehen laesst sich jeder Schritt mit "git status",
"git log --oneline" und auf der GitHub-Seite im Reiter "Actions".


TESTS VOR JEDEM RELEASE (ab 0.60)
---------------------------------------------------------------------------
Bei jedem Bau laufen alle Tests (test_*.py) auf Linux und eine Auswahl auf
Windows (Jobs "Tests Linux" und "Tests Windows" im Reiter "Actions"). Ist
ein Test rot, entsteht kein Release und keine Testversion. Das ist gewollt:
ein roter Test wird repariert, nicht uebersprungen.

NOTAUSWEG - nur mit Nicos ausdruecklichem OK, nie von Claude allein:
  1. Auf GitHub: Settings > Secrets and variables > Actions > Variables >
     "New repository variable", Name TESTS_UEBERSPRINGEN, Wert ja.
  2. Im roten Lauf oben rechts "Re-run jobs" > "Re-run failed jobs".
     Die Test-Jobs werden dann uebersprungen, der Release wartet nicht
     mehr auf sie (Bau und Update-Test laufen weiter wie immer).
  3. Danach die Variable TESTS_UEBERSPRINGEN sofort wieder loeschen.


EINEN FRUEHEREN STAND WIEDERHERSTELLEN
---------------------------------------------------------------------------
  1. git log --oneline
     zeigt eine Liste wie:
       ed59ebb Version ueberall gleich: build.py --setze-version ...
       52f9d1f Version 0.21: Linux-Installer lauffaehig ...

  2. Einzelne Datei auf einen frueheren Stand setzen:
       git checkout 52f9d1f -- app_gui.py
     Oder alle Dateien:
       git checkout 52f9d1f -- .
     Danach zeigt "git status" den Unterschied zum aktuellen Stand. Mit
     einem neuen Commit wird der aeltere Stand zum aktuellen Stand.

  Nichts geht kaputt, solange gesicherte Staende existieren. Im Zweifel
  lieber Claude fragen, bevor ein Befehl ausgefuehrt wird, dessen Wirkung
  unklar ist.
